# Безопасность

Не публикуйте уязвимости вместе с реальными данными, ключами, резервными кодами или паролями в открытых Issues. Используйте приватный канал владельца репозитория либо GitHub Private Vulnerability Reporting, если владелец его включил. Публичный контакт для сообщений о безопасности владелец задаёт самостоятельно.

## Встроенные меры

- Серверные проверки роли на `/admin` и `/admin/export/*`, ограничение кабинета собственной аудиторией.
- CSRF для POST-форм, параметризованный SQL, автоэкранирование Jinja, HTTPS-only ссылки в публикациях.
- Werkzeug scrypt для паролей и резервных кодов. Одноразовая замена кода; отзыв старых сессий при смене/восстановлении пароля.
- HttpOnly, SameSite=Lax, Secure-cookie в production; ключ только из окружения, обязательная минимальная длина.
- CSP, nosniff, Referrer-Policy, отсутствие кеширования динамических страниц, ограничение размера запросов и частоты отправки форм.
- Случайный первоначальный пароль администратора, закрытый bootstrap-файл; нет общего стандартного пароля.
- Релизный ZIP строится по списку разрешённых файлов. Базы, ключи и реальные заявки не включаются.

## Обязанности при размещении

Настройте HTTPS, доверенный reverse proxy, лимиты по реальным IP, постоянный диск с надлежащим расположением, права доступа, обновления зависимостей, безопасные backups и регламент восстановления. Приложение не доверяет произвольным forwarded-заголовкам; за прокси встроенный limiter может видеть общий IP, поэтому ограничения дополнительно настраивают на proxy.

Нет MFA, подтверждения email, почтового восстановления и автоматической отправки писем. Резервный код — секрет с возможностью смены пароля; храните его в менеджере паролей. Потерянный код требует ручной безопасной проверки личности организатором. Доступ к внешним файлам защищается самим хранилищем, а не только видимостью ссылки в кабинете.

Папки `instance/`, backups и exports нельзя раздавать reverse proxy как статику. Первоначальный `admin-access.txt` удалите после изменения пароля. Не запускайте Flask debug публично. Используйте один экземпляр приложения с SQLite; горизонтальное масштабирование требует отдельного проектирования БД.

Аудит зависимостей отражает известные публичные уязвимости на момент проверки, не доказывает отсутствие иных проблем. Автоматизированные проверки не являются независимым пентестом.

Если секрет или база уже попали в Git-историю, одного удаления файла недостаточно: отзовите/смените секрет, ограничьте доступ к данным, очистите историю и копии согласно регламенту инцидента. Не помещайте новый секрет в следующий коммит.
