# Загрузка в GitHub и публикация

## 1. Загрузка через Git (рекомендуется)

1. Распакуйте релизный ZIP. Перейдите в папку, где лежат `app.py`, `.gitignore` и `README.md`, а не во внешнюю папку архива.
2. Создайте на GitHub пустой репозиторий, например `tourism-without-borders`. Не добавляйте автоматически README, лицензию и `.gitignore`: они уже подготовлены в проекте (лицензию выбирает владелец отдельно).
3. Откройте терминал в корне проекта:

```bash
git init -b main
git add .
git status --short
git diff --cached --name-only
```

4. Проверьте список: там должны быть `.env.example`, `.github/workflows/ci.yml`, исходники и документация. **Не должно быть** `.env`, `instance`, `session.key`, `admin-access.txt`, SQLite-баз, экспортов или реальных заявок.
5. Сделайте коммит и привяжите URL своего пустого репозитория:

```bash
git commit -m "Prepare production-ready source release"
# Вместо строки ниже подставьте HTTPS URL, скопированный в своём репозитории.
git remote add origin "URL_ВАШЕГО_РЕПОЗИТОРИЯ"
git push -u origin main
```

Выполните обычную авторизацию GitHub через менеджер учётных данных/браузер. Не вставляйте токены в URL remote и не сохраняйте их в исходниках.

После push откройте вкладку **Actions**: подготовленный workflow устанавливает зависимости, проверяет код, тесты, доступность, аудит зависимостей и формирует чистый ZIP как артефакт. Выполнение на GitHub требует доступа к сети для установки пакетов и браузера. Workflow подготовлен, но фактический запуск в вашем аккаунте происходит только после загрузки.

### Через веб-интерфейс

В пустом репозитории выберите **Add file → Upload files** и загрузите **распакованное содержимое**, а не один ZIP. Убедитесь, что скрытые файлы `.gitignore`, `.env.example`, `.dockerignore` и папка `.github` тоже загружены (проводники иногда их скрывают). Если браузер не переносит скрытые папки, используйте Git. Нельзя просто выложить ZIP и ожидать, что GitHub развернёт приложение.

## 2. Выбор хостинга

Это серверное Flask-приложение. **GitHub Pages и статический hosting не подходят:** они не исполнят Python, не сохранят заявки и не обеспечат авторизацию.

Выберите Linux-хостинг/VPS либо контейнерную платформу с:
- Python 3.13 или поддержкой Docker;
- постоянным диском для SQLite и служебных файлов;
- HTTPS и собственным доменом;
- закрытыми переменными окружения и доступом к приватным файлам администратора;
- надлежащим географическим размещением данных, резервными копиями и контролем доступа.

Тариф, регион, домен, TLS и правила обработки данных выбираются и настраиваются владельцем. Они не создаются автоматически загрузкой кода в GitHub.

## 3. Публикация без Docker

1. Подключите репозиторий к хостингу или клонируйте его на сервер.
2. Создайте виртуальное окружение и выполните `pip install -r requirements.lock`.
3. Укажите build/install command: `pip install -r requirements.lock`.
4. Укажите start command: `gunicorn --config gunicorn.conf.py app:app`.
5. В закрытых настройках хостинга задайте:

| Переменная | Значение |
|---|---|
| `APP_ENV` | `production` |
| `SECRET_KEY` | собственный криптографически случайный ключ, минимум 32 символа |
| `COOKIE_SECURE` | `1` |
| `INSTANCE_DIR` | путь к постоянному диску, выделенному приложению |
| `PORT` | порт, назначенный платформой, либо `3000` |
| `WEB_CONCURRENCY` | `2` для небольшого проекта |

Ключ можно сгенерировать локально: `python -c "import secrets; print(secrets.token_hex(32))"`. Сохраните результат только в менеджере секретов/закрытом `.env`. Не используйте один ключ для тестового и боевого окружения.

6. Подключите постоянный диск и дайте системному пользователю приложения права записи. Только один экземпляр приложения должен использовать эту локальную SQLite-базу. Не размещайте SQLite на эфемерном или неподходящем сетевом диске.
7. Настройте reverse proxy с HTTPS. Порт Gunicorn не должен быть единственным незащищённым публичным входом. Настройте перезапуск процесса средствами хостинга/systemd, лимиты запросов, журналы без персональных query-параметров, ротацию логов и резервные копии.
8. Откройте **HTTPS-адрес** домена, проверьте `/`, `/register`, `/login`, `/recover`, `/privacy` и ресурсы `/static/`.

Приложение должно быть размещено в корне домена, а не под префиксом вида `/my-repository/`. Все текущие маршруты предполагают корень. Прямое обновление `/account` и `/admin` обслуживает Flask; SPA-fallback на `index.html` не нужен.

## 4. Вариант Docker

Подготовлены Dockerfile и allowlist `.dockerignore`. Локально:

```bash
cp .env.example .env
# Заполните SECRET_KEY. Сохраните APP_ENV=production, COOKIE_SECURE=1.
# Для контейнера установите INSTANCE_DIR=/data и PORT=3000.
docker build -t tourism-site .
docker volume create tourism-data
docker run -d --name tourism-site --restart unless-stopped \
  --env-file .env -p 127.0.0.1:3000:3000 \
  -v tourism-data:/data tourism-site
```

Перед контейнером настройте HTTPS reverse proxy. Пример привязывает порт только к loopback хоста, не делает его общедоступным. Для управляемой платформы используйте её способ маршрутизации и монтирования диска.

Контейнер работает от непривилегированного UID 10001. Если вместо named volume монтируете существующий каталог, заранее задайте права этому UID; иначе SQLite не сможет записать данные. `INSTANCE_DIR` в `.env` должен совпадать с точкой монтирования.

**Ограничение проверки:** Docker Engine в среде подготовки отсутствовал. Dockerfile подготовлен и проверен чтением, но сборку контейнера необходимо выполнить вручную командой выше. Production-запуск самого приложения через Gunicorn и установку из lock-файла проверили отдельно.

## 5. Настройка проекта после запуска

1. Приватно прочитайте `admin-access.txt` в каталоге `INSTANCE_DIR` на сервере. В контейнере файл можно прочитать командой `docker exec tourism-site cat /data/admin-access.txt` — вывод содержит пароль, не публикуйте его в скриншотах или журналах.
2. Войдите через `/login`, измените технический email и пароль в «Мой профиль», затем удалите bootstrap-файл доступа.
3. В «Настройки» заполните наименование, адрес и контакт оператора персональных данных.
4. Утвердите политику/согласие, конкретные сроки хранения, регламент удаления и правовые основания. До этого не начинайте сбор реальных данных.
5. Добавьте реальные даты, места, материалы, согласованных партнёров. Не обещайте удостоверения или доступность объектов до согласования/проверки.
6. Отправьте собственную тестовую заявку без чувствительных данных. Проверьте уникальный номер, сохранение, восстановление по коду, кабинет, статусы, группы, посещаемость и выгрузки.
7. Проверьте, что участник получает 403 на `/admin` и экспортах, а гость перенаправляется ко входу. Проверьте отсутствие доступа к `/.env` и `/instance/`.
8. Удалите тестовую заявку после проверки.

## 6. Сохранение данных и обновления

Релизный ZIP намеренно не переносит рабочую базу, секреты, пользователей, административные публикации и реквизиты из действующего экземпляра. Для переноса существующего сайта отдельно сделайте закрытую резервную копию через SQLite backup API и безопасно перенесите её на постоянный диск. Это не должно проходить через публичный GitHub.

Перед обновлением сделайте backup БД и ключей, проверьте релиз на копии, остановите приложение на время несовместимых миграций. В этой версии автоматически и без удаления строк добавляется колонка `users.auth_version` для отзыва старых сессий; остальные таблицы сохраняются. На существующей базе используйте тот же SECRET_KEY (либо содержимое прежнего закрытого `session.key` через переменную), иначе потребуется повторный вход. При компрометации ключа его нужно заменить.

Сохраняйте backups вне репозитория, с шифрованием и политикой удаления. Экспорты, обращения и внешние документы могут содержать персональные данные. Обновление кода не является их удалением.
